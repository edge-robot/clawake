## Behaviour changes for operators

- **New command** `clawake rollout -c <inv> [-m <member>]... [--plugin <id>=<tgz>]... [--execute]`.
  - Exit codes: 0 = success or preview; 1 = a host read failed in the preview, or a
    failure during `--execute` (summary and hint are printed); 2 = invalid request, or an
    inventory load error.
  - Backups go to `.backups/` in the working directory, the same location `upgrade` uses.
- **Decisions I made where the prompt left room** (please confirm):
  - Members without any planned change get no backup (`backup: none (no change planned)`).
    This keeps the no-op and idempotent runs free of writes. The overlay copy is taken
    only when pins change.
  - All backups are taken before the first deploy (not interleaved per member), so a
    failed backup aborts before any deploy.
  - `rollout` does not prune `.backups/`. The existing `prune_backups(prefix=f"{name}-")`
    would also match another member named `<name>-…` (see *Out-of-scope findings*).
  - `rollout` does not retire legacy services and does not run the A2A env-file check,
    because that check reads token values. `setup` still does both.
  - A `--plugin` applies to every selected member that declares the id. Restrict it
    with `-m`.
  - Summary column `pins`: `yes`, `no` or `-` (no new pin for that row).
- **#27:** after `upgrade --execute` / rollback, a JSON inventory without `runtime_pins`
  stays valid JSON. It is rewritten with 2-space indent and `ensure_ascii=False`; key
  order is preserved. A file with another indent is normalised to 2 spaces. Config
  backups keep the inventory's suffix (previously always `.yaml`). The prune prefix is
  unchanged.
- `upgrade`, `setup`, `sync-plugins`, `status`: no other behaviour change.

## Open points and risks

- **OpenClaw facts:** the rollout relies on no new OpenClaw behaviour. It reuses the P2
  commands (`openclaw plugins install --force --accept-capabilities`,
  `plugins list --json`, `plugins inspect --runtime --json`) and the P1 `/readyz` probe.
  I did not re-check them against https://docs.openclaw.ai/ in this task, so they are
  unverified here and rest on the P1/P2 reports and the live evidence.
- **Two restarts per member** for a plugin rollout: one for the new archive mount, one
  after the install (P2 semantics, "restart only on change"). Expect about 2 × 46–60 s
  per member. A single restart would need an install from a staged mount, which is
  outside this scope.
- **`backup_instance` contents:** the archive includes the member's runtime state
  directory, which can contain OpenClaw state. This is existing semantics, as the prompt
  requires. Clawake never prints it, but the archive is as sensitive as the state
  directory.
- **No backup pruning in `rollout`** (see decision above). `.backups/` grows with each
  rollout that changes members.
- `rollout` re-plans nothing between members. `apply_artifacts` fails closed with
  "Configuration changed since planning" if a later member's files changed during the
  run.
- **Proposed `docs/architecture.md` text** (Lifecycle contracts; the drift marker is in
  `services/rollout.py`):
  > `rollout` composes the same steps per member: it validates a candidate state
  > (inventory + runtime pin overlay + new archive plugin pins) in memory, previews setup
  > actions, plugin decisions, grants and backups read-only, and with `--execute` takes all
  > backups first, then deploys, acts, waits for readiness, syncs and verifies plugins
  > one member at a time. New plugin pins are committed to the overlay only after the
  > member verified; the first failure stops the rollout. Plugin installation is therefore
  > performed by `sync-plugins` and by `rollout`.

## Out-of-scope findings

- `src/clawake/cli.py:573` (`upgrade`, prune after success) and
  `src/clawake/services/backup.py:105` (`prune_backups`): the prefix `f"{instance.name}-"`
  also matches backups of a member whose name starts with `<name>-` (for example `lead`
  and `lead-2`). Such a prune could delete the other member's backups. Not fixed.
- `src/clawake/services/upgrade.py` `backup_config`: the timestamp has one-second
  resolution, so two backups within the same second overwrite each other. Not fixed.
- `src/clawake/services/upgrade.py` YAML path: block-style writes still use a plain
  `write_text`, which is not atomic (pre-existing; JSON writes are now atomic). Not fixed.
