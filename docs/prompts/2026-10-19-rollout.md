# P3b: `clawake rollout`, plus JSON-preserving inventory writes (#24, #27)

## Goal

1. **One command per rollout.** One reviewed preview, then backup → apply → targeted
   restart → readiness → plugin sync → verify → pin commit → summary. Stop at the first
   failure. Plugin pins come from the command line and are committed to the runtime pin
   overlay only after a verified rollout.
2. **Fix #27.** Clawake must never corrupt a JSON inventory and must back it up with the
   right suffix.

- **Decisions:** `docs/ADR.md`, ADR-003 item 5 (`rollout`) and ADR-004 (overlay;
  "`rollout` writes plugin pins only after a verified rollout"). Both are binding.
- **Issues:** edge-robot/clawake#24 (target workflow in the issue body) and
  edge-robot/clawake#27 (bug).
- **Building blocks, all accepted. Reuse them; do not duplicate them:**

  - `services/member_ops.py` (P2):

      `verify_pinned_plugins`, `plugin_sync_summary`;
    - output: `render_table`.
  - `services/runtime_pins.py` (P3a): `read_pins`, `set_plugin_pin` (atomic, 0600,

  - `services/backup.py`: `backup_instance`, `prune_backups`.

  - `_format_image_value` can write a literal `None`.
  - `backup_config` uses a `.yaml` suffix for JSON files.

## Binding constraints and prohibitions

1. **CLI.**
   ```
   clawake rollout -c <inventory> [-m <member>]... [--plugin <id>=<path-to-tgz>]... [--execute]
   ```
   v1 only; v2 gets a clear error. Without `--plugin` it reconciles the selected members
   (setup + plugin sync). `--plugin` requires `runtime_pins` in the inventory; without
   it, exit 2 with a hint to `clawake pins init`.
2. **Candidate state in memory.**
   - For each `--plugin`:
     - check that the plugin id is declared as an **archive** plugin on every selected
       member that gets it;
     - check that the file exists and is readable;
     - compute its `sha256`;
     - read `package/package.json` `version` from the tgz;
     - reject a `version` that cannot be read.
   - Build the candidate effective inventory = inventory + overlay + new pins **in
     memory**, through the same validation path as `load_inventory`.
   - **Do not write the overlay yet.**
3. **One combined preview.** Never mutate in the preview; reading host state read-only is
   fine. It shows, per member:
   - the setup action (`restart` / `start` / `none`) with reasons;
   - for each plugin: old → new pin (version, digest prefix) and the planned action
     (`skip` / `install`, with reasons);
   - grant changes;
   - the readiness now;
   - the backups that would be taken.

   It ends with `Members to restart:` and `DRY RUN rollout complete. Re-run with
   --execute.`
4. **`--execute` order, per selected member, sequentially:**
   1. **Backups first.** Use `backup_instance` for each selected member (existing
      semantics), plus a copy of the current overlay. Print their paths. Abort if a
      backup fails.
   2. **Apply.** Render and deploy from the **candidate** state, then reload systemd.
   3. **Act** per the setup plan (restart / start / none), then wait for readiness
      (start window).
   4. **Plugin sync** for that member from the candidate state, using P2 semantics: wait,
      install or skip, ledger, config/grants, restart only on change, wait, verify the
      pinned version.
   5. **Commit the pins.** Only after the member verified successfully, commit that
      member's new pins to the overlay with `set_plugin_pin`. If the overlay is shared,
      writing once per member is fine.
   6. **Stop on the first failure.**
      - Members after it are not touched.
      - The overlay keeps the old pins for the failed member and every later member.
      - Print the rollback hint: the deployed state of `<member>` now differs from the
        pins, and the backups are at `<paths>`. To return to the committed pins, run
        `clawake rollout -c <inv> -m <member> --execute` without `--plugin`.
      - Exit 1.
5. **Summary table** at the end, also on failure: member, setup action, plugin, old→new
   version, digest prefix, result, readiness, seconds to ready, and pins committed
   (yes/no).
6. **No unbounded waits, no retries.** Every host call goes through the existing seams.
   The rollout never reads or prints secrets.
7. **#27 fix.**
   - All inventory writes keep the file format. JSON stays valid JSON with stable key
     order and 2-space indent. YAML keeps the current behaviour.
   - `None` is never written as a literal; omit the key or raise.
   - `backup_config` keeps the original suffix.
   - Each item needs a regression test. The test for the JSON corruption must fail on
     the base code first.
8. **Scope limits.**
   - Do not change the semantics of `setup`, `sync-plugins`, `status` or `upgrade`,
     except #27.
   - No image upgrades in `rollout`; `upgrade` stays the image path.
   - No new dependencies. Public repository: synthetic data only. Never run `--execute`,
     `podman`, `systemctl` or `openclaw` yourself.

## Steps

   the checks and record the base test count.
2. Write the #27 regression tests first; they must fail. Then fix #27 in its own commit
   (`Refs: edge-robot/clawake#27`).
3. Write the `rollout` tests first, with fakes for systemd, readiness, `podman exec` and
   the clock, and synthetic tgz files built in `tmp_path`. Cover:
   - a happy single-member plugin rollout: preview shows old→new, nothing is written; with
     `--execute` the order is backup → deploy → restart → wait → install → wait → verify
     → pin commit, and the other member is untouched;
   - a failure at readiness after the restart: no pin commit, the next member is
     untouched, the hint is printed, exit 1;
   - a failure at the install: no pin commit, no ledger entry;
   - a backup failure aborts before any deploy;
   - an id that is not declared as an archive plugin, a missing file, an unreadable
     version, and a missing `runtime_pins` → exit 2 before anything else;
   - a rollout without `--plugin` on an unchanged team is a no-op (no restart, no
     install);
   - an idempotent second run with the same `--plugin` → `skip`, no restart, overlay
     unchanged (no new backup in `pins-backups/`).
4. Implement, e.g. `services/rollout.py` with thin CLI wiring.
5. Document `rollout` in `docs/manual.md`. Propose `architecture.md` text in the report.
6. Run the checks, commit and write the report.
